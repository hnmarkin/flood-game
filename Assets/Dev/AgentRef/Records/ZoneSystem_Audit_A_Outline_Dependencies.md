# Audit A — ZoneThinOutlineByHover Dependencies

Read-only audit, 2026-10-15; working-tree sources/assets, including pre-existing edits. Only this report was created; no Unity execution or gameplay modifications.

### A. Existing Architecture

- `Assets/Dev/Dev_ZoneSystem/Scripts/ZoneSystem/` contains `ZoneController.cs`, its owned `ZoneIndex.cs`, pure `ZoneGeometry.cs`, and `ZoneBoundaryEdge.cs`; no outline gateway exists yet.
- Existing GEOID/tile APIs: `TryGetGeoidAtNormalizedTile`, `TryGetZoneTiles`, `GetAllZoneTiles`, `ContainsTile`; world lookup: `TryGetZoneTilesAtWorld`; boundaries: `TryGetBoundaryTiles` / `TryGetBoundaryEdges`. Reuse these.
- Existing coordinate APIs: `NormalizedTileToCell`, `CellToNormalizedTile`, `TileOrigin`, `TerrainTilemap`; normalized tiles are relative to compressed Tilemap bounds, not JSON row/column or padded simulation coordinates.
- Existing lifecycle APIs: `Configure`, `IsZoneLoaderReady`, `EnsureZoneIndexReadyForExternalUse`, `RebuildZoneIndex`, `InvalidateZoneIndex`, `IsInitialized`, `ZoneCount`. Index building requires loader payload, nonempty `cellToRC`, `geoidGrid`, map data and terrain; queries lazily initialize. No readiness/change event exists; `GetAllZoneTiles` and uninitialized `TileOrigin` currently have initialization/bounds side effects.
- `ZoneGeometry` already calculates four-neighbor boundary tiles/edges; `ZoneBoundaryEdge` holds orientation, normalized grid line, interior/exterior tiles and map-exterior status. X edges are vertical, Y horizontal; its legacy barrier conversion adds `(1,1)` solely for simulation.
- `Assets/Dev/Scripts/Flood/FloodDefenseBoxStamp.cs` forwards zone queries to `ZoneController`, configures it through component lookup/global discovery/runtime creation, and forwards barrier state/events. `Assets/Dev/Dev_BarrierSystem/Scripts/BarrierSystem/BarrierController.cs` owns placement, previews, committed barrier visuals and mode changes; those visuals are separate from this audit's seven channels.
- `Assets/Dev/Scripts/Zones/ZoneThinOutlineByHover.cs:81–139` polls `Input.mousePosition`, projects through its camera, looks up via the stamp, and redraws when GEOID or HashSet identity changes; no UI-pointer exclusion. Its own four-neighbor boundary builder duplicates existing geometry and converts normalized corners through the stamp; tile requests already contain absolute Tilemap cells. Requests draw each zone separately, including shared seams, rather than outlining a merged union.
- Rendering (`:316–511`): seven growing LineRenderer pools, one world-space two-point line per edge, prefab cloning or generated children, constant width, View alignment, Stretch textures, zero caps/corners. Shared assigned material or fallback URP/Sprites/Unlit material; request colors use vertex colors plus `_BaseColor`/`_Color` property blocks. Both scenes override width to `0.08` (code default `0.045`), yellow hover, Z `-0.1`, Default sorting layer/order `1000`, assigned scene LineRenderer and `Assets/Dev/Ash_dev/ash_prefabs/ZoneLineMaterial.mat`.
- `Awake` resolves camera/stamp; public show calls retry stamp discovery. Missing stamp hides all pools during `Update`; hover also clears without camera/when disabled by `outliningEnabled`. Persistent segments/counts survive visibility hiding; requests are not retained for map rebuilds. No component `OnDisable`/`OnDestroy` cleanup or runtime-material disposal exists; children follow GameObject destruction, not component disable.

### C. Existing Outline Channels

- **Hover** (`_linePool`): follows mouse; private `ClearOutline` on zone miss, hover disable, missing camera/stamp, or barrier suppression; independent of every overlay.
- **Baseline risk** (`_baselineLinePool`): subset/all-zone callers and every legacy generic persistent/risk alias replace this one channel; `ClearBaselineRiskOutlines`, `ClearPersistentZoneOutlines`, `ClearRiskOutlines` clear only it.
- **Live flood risk** (`_liveFloodLinePool`): dedicated show/clear; HighRiskManager and FloodImpactOverlayManager explicitly hide one another's overlays at consumer level, despite independent renderer storage.
- **Shelter candidate zones** (`_shelterZoneLinePool`): candidate/placement preview; `ShowShelterAssociatedZoneOutlines` replaces only zone lines.
- **Shelter candidate tiles** (`_shelterTileLinePool`): four edges per requested absolute cell; `ShowShelterCandidateTiles` replaces only tile lines; `ClearShelterCandidateHighlights` clears BOTH candidate channels, preserving placed outlines.
- **Placed shelter zones** (`_placedShelterZoneLinePool`): persists across candidate toggles; dedicated show/clear, refreshed on shelter changes and cleared by shelter component disable/configuration.
- **Communication zones** (`_communicationZoneLinePool`): dedicated tower-hover show/clear; uses persistent visibility rules even though its interaction lifetime is hover.
- All six non-hover pools retain counts/segments while barrier-hidden and restore on exit with default flags; each show replaces its target, each clear zeros only its specified count(s). No per-owner arbitration, cross-request deduplication, or global public clear exists. Labels, ghosts and barrier Tilemap previews are outside these pools.

### D. Compatibility Risks

1. **Critical — component identity/wiring:** GUID `71bfc9ffc1b314ef7a54476c563601a5`, component `704415076` on `ZoneBoundaryLine`, occurs once in `Assets/Game/Content/Scenes/PlayableTilemap.unity:4131` and once in `Assets/Dev/Dev_UINavigation/Scenes/Dev_UINavigation.unity:4132`; each has six typed consumer fields pointing to it (12 total, including dormant legacy). All six scripts also use `FindFirstObjectByType<ZoneThinOutlineByHover>`. Immediate type removal breaks compilation; component replacement loses typed wiring/discovery and authored settings. All 56 scenes/159 prefabs are YAML; no matching prefab component or serialized outline-method UnityEvent was found.
2. **High — coordinates/geometry:** treating `TileOutlineRequest.Cell` as normalized applies origin twice; treating edge grid lines as padded barrier coordinates shifts outlines. Preserve negative origins, holes, separate zone seams and map-exterior edges; never filter exterior edges as barrier physics may do. Convert X endpoints by `(0,1)`, Y by `(1,0)`, through existing controller/Tilemap conversions.
3. **High — initialization/cache:** controller is a separately wired scene object, despite older documentation suggesting colocation; stamp/barrier fallback may create/configure it in `Awake`. No readiness event or automatic map-change invalidation exists; index queries initialize lazily, boundary lists are recomputed, and tile sets remain mutable. Eager one-shot requests before readiness can draw nothing; persistent lines stay stale after rebuild unless reissued. Baseline waits for readiness; towers retry generation up to 120 frames; shelter checks readiness on demand.
4. **High — channel/lifecycle collisions:** collapsing pools erases candidate tiles, candidate zones, placed coverage or tower hover when another overlay clears. Baseline's two writers intentionally replace/clear one pool; reactivating legacy Shelter makes two shelter implementations contend for the same three pools. Keep baseline/live mutual-hide logic and label lifetimes in their consumers; barrier entry hides cached lines rather than clearing them.
5. **Medium — visibility flags:** both scene flags are true. `Update` gates barrier hiding through `hideWhileBarrierModeIsActive`, whereas show methods independently check `hidePersistentWhileBarrierModeIsActive`; nondefault combinations differ. Preserve recorded behavior during extraction and verify combinations before intentional fixes; `outliningEnabled` governs hover only.
6. **Medium — rendering/cleanup:** replacing the scene LineRenderer/material or using code defaults changes width, alpha, sorting and Z. Disabling only the old MonoBehaviour currently leaves child lines alive; generated material is never explicitly destroyed. Give the eventual renderer explicit ownership/disposal without silently clearing another consumer's channel or destroying assigned assets.

### E. Proposed Architecture

- `ZoneController`: sole new external outline gateway, e.g. additive `SetZoneOutlines(channel, requests)`, `SetTileOutlines(channel, requests)` and `ClearOutlines(channel)`; validates readiness/inputs, uses existing index/boundary/conversion APIs, prepares geometry and submits it to rendering. Preserve the paired candidate-clear contract and raw normalized-tile-set compatibility path.
- `ZoneGeometry`: reuse its current boundary calculations; only add minimal endpoint/tile-corner helpers if useful. Keep calculations independent of input, renderers and barrier/water simulation; never rebuild another zone lookup.
- `ZoneOutlineRenderer`: one rendering owner with seven independent pools, per-request colors, existing appearance settings, visibility separate from cached channel contents, and owned-resource cleanup. An internal helper can suffice; another serialized MonoBehaviour is optional. Receive geometry/settings from the controller, without calling back into it.
- `ZoneHoverHandler`: interaction role only—pointer/camera lookup, current-zone state and hover submissions via controller. Initially retain this logic in the old component; introduce a separate handler only when retiring that component warrants it. Read existing barrier mode/property or event without changing BarrierSystem; unsubscribe any new event subscriptions on disable.
- **Temporary adapter is necessary:** retain `ZoneThinOutlineByHover` class, script GUID, serialized settings/references, all 19 signatures/overloads and global request structs. Forward legacy calls to the controller, transfer appearance/visibility settings explicitly, and ensure only one owner draws each channel. This protects Shelter, Communication, Risk and Water consumers during the initial migration.

### F. Recommended Migration Stages

1. Extract existing pooling/material/drawing behavior into an internal `ZoneOutlineRenderer` behind the unchanged facade; retain geometry queries, hover, serialized settings and every consumer. Compare all seven channels with current visuals before changing data flow.
2. Add the controller outline gateway using existing zone geometry/conversions; make legacy methods forward through it, including generic baseline aliases and paired candidate clear. Transfer renderer ownership/configuration once; avoid duplicate drawing and lower-level callbacks into the controller. No initial edits to ShelterSystem, CommunicationSystem, RiskSystem, WaterSystem or BarrierSystem.
3. Route hover through the gateway, optionally extracting its handler; preserve barrier visibility/cache rules using existing state access. Validate startup readiness, map rebuild refresh policy, mixed overlays, clear isolation, barrier entry/exit and component disable in both scenes; add owned-resource cleanup deliberately.
4. In later separately scoped changes, migrate five active consumers individually, then dormant legacy compatibility; verify Inspector assignments and runtime discovery before removing old public dependencies. Remove the adapter/component only after all code and serialized references are migrated; retain legacy interfaces until that explicit retirement stage.
